# 重写方案（v3 分支）：先建信任，再让多 agent 并行

写于 2026-11-02，基于 `v2` 的 HANDOFF-v4（`b8a2af6`）。候选人对上一轮不满意，要求重新搭多 agent 框架。本文先定组织（谁干什么、谁审谁、怎么升级信任），再定支撑这个组织的代码结构，最后定启动顺序。

## 目标

候选人拿到一份能办 H-1B 的工作。她的原话：「这事儿就四步」——**1 搜全、2 筛准、3 投出去、4 两份名单**（她自己投的、小公司外联的）。整个系统要做到她不用逐条检查也能相信结果，并且越跑越不需要她。

## 视频的逻辑，套到这件事上

Lauren Tan 的顺序是：**先让一个 agent 的输出可验证 → 再让它无人值守 → 再开很多个并行**。并行是信任的结果，不是手段。「没有信任，开 100 个 agent 只会得到一堆垃圾 PR」。

| 视频 | 投简历 |
|---|---|
| 1 个总管 + 几个经理 + 大量工人 | 1 个总协调 + 每一步一个经理 + 每个来源 / 每个 ATS / 每条规则一个工人 |
| Verification：agent 自己跑真实应用验证 | 每个工人的完成证据是「东西本身」：真实招聘板读全了、真实表单读回一致、确认邮件到了 |
| Feature Map | 公司地图（每家目标公司的官方入口、ATS、能否读全）、ATS 地图（字段、上传、验证码、账号、确认页） |
| Skills + 用 eval 测 skill | 每个角色一个 skill；用盲测检验 skill：她的标注、历史拒信、历史表单都是 eval 集 |
| 信任曲线 → 自动合并 PR | 每个角色、每个 ATS 各有信任等级；代码 PR 可以较早自动合并（可撤回），**提交申请**的自动化最晚放开（撤不回） |
| Benny：自动复现 bug 报告 | 每封拒信、每次读回不一致、每个被她纠正的答案，都自动变成一个可复现的工单 |
| Local → Cloud | 本会话里跑通一个单元 → 云端会话跑经理 → 定时任务跑每日流水线（她点头后） |
| 五层金字塔，每纠正一次往上沉淀 | 审核者抓到的错第二次出现，就必须变成测试或类型，而不是再审一遍 |

## 一、上一轮的多 agent 为什么没建立起信任

HANDOFF-v4 和 `docs/program/notes.md` 里的事实，按视频的标准看：

1. **一开始就并行，没先跑通一个单元。** 约 20 个工人、十几个审核，sonnet 工人首轮 5/5 被退回。视频和 orchestrate playbook 都要求先拿一个单元走完「任务书 → 工人 → 审核 → 合入」，确认任务书没问题再铺开。
2. **工人的完成证据是代理指标，不是东西本身。** 覆盖率用第三方列表抽样，6 轮在 67%–87% 之间来回跳，多数轮次在修尺子。
3. **审核者一直在抓同一类错，但这些错没被沉淀成结构。** 重复岗位出现 3 次、误判下架出现 4 次，每次都靠审核者重读。审核成本翻倍，工人的信任等级也永远升不上去。
4. **工作和数据两个组织混在一起。** 同一批 agent 既改代码，又跑搜索、写数据、出数字。改代码的错和跑数据的错搅在一起，谁也说不清一个数字变了是因为代码变了还是数据变了。
5. **按「步骤」切任务，没按「文件归属」切。** 并行工人改同一个 `src/sources/fetch.ts`、`config/watchlist.yaml`，频繁冲突；禁止改接线文件，新抓取器就接不上。
6. **只有总协调和工人两层，没有经理。** 总协调直接盯 20 个工人，读每份报告，上下文被撑爆，判断力下降（继续派活、没有复盘）。
7. **没有「每轮目标数字有没有动」的硬性停止条件**，规则写进 notes.md 以后也没执行。

## 二、新组织

### 两个组织，分开

| | 建造组（改代码） | 运营组（每天跑流水线） |
|---|---|---|
| 产出 | PR（代码、测试、fixture、地图、skill） | 数据（catalog、ledger、待办清单、每日页面）和工单 |
| 能写 | 自己负责的目录 | 只有 `data/` 下的运行产物，**不改代码、不改 policy** |
| 怎么证明对 | CI + 非作者审核者 + 一次真实运行的证据 | 代码里的不变式和阶段门 + 盲审抽样 |
| 发现问题时 | 修 | 写一张工单（可复现：输入、期望、实际），交给建造组 |

上一轮的「尺子和东西搅在一起」靠这条分界解决：数字只由运营组用已合入的代码产生，建造组不报运营数字。

### 拓扑

```
总协调（1 个持久云端会话；只决定、派活、读产物、打分；不写代码、不跑流水线）
│   状态：docs/program/notes.md（只它写）、docs/decisions.tsv
│
├─ 搜索经理（第 1 步）      归属：src/sources/**、config/watchlist.yaml、公司地图
│   ├─ 工人：一个来源 / 一组公司一个，各写自己的目录
│   └─ 审核：按公司检查读全（代码）+ 每周第三方抽样（另一个模型，盲审）
├─ 筛选经理（第 2 步）      归属：src/discover/triage*、src/policy/**、eval 集
│   ├─ 工人：一条误拒原因一个；模型初筛工人（haiku，看不清的岗位）
│   └─ 审核：盲审员（另一个模型，只读岗位原文和 brief）+ 拒信回放
├─ 投递经理（第 3 步）      归属：src/ats/**、src/answer/**、ATS 地图、fixture
│   ├─ 工人：一个 ATS 一个；问题→事实映射工人
│   └─ 审核：提交审核员（截图 + 读回 + 计划 + 她的资料，逐项核对）、verify-apply
└─ 名单经理（第 4 步，最后启动） 归属：手动名单、外联名单的生成
```

- **三层封顶**（总协调 → 经理 → 工人）。每个经理手上同时最多约 10 个工人，完成一个补一个。经理只给总协调交一份汇总，不转发工人的原始报告。
- **一个目录一个主人。** 共享文件（`src/domain/**`、`cli.ts`、`package.json`）只归总协调指定的「平台」工人，其他工人需要改时提工单。注册表由目录自动生成，加一个来源或 ATS 不需要改任何共享文件。
- **一个单元 = 一个 PR，合入 `v3`。** 每个 PR 只有一个主人（作者），由它推送、rebase。审核者不是作者，用另一个模型（这里只有 Claude 系列：作者 sonnet 就由 opus 审，反之亦然；盲审员用不同 prompt，只读原始材料），审的是当前 head 的 diff 和证据，不读工人的总结。
- **任务书（kickoff）必须写明**：她的目标、这个单元的完成证据（命令 + 期望输出，或真实页面的读回结果）、可写和不可写的路径、禁止的动作、token 预算。写不出证据，说明这个单元还没切好。

### 怎么跑起来（这个环境里的具体手段）

| 角色 | 载体 |
|---|---|
| 总协调 | 一个持久云端会话（就是本会话或新开一个），PR 事件订阅唤醒它；不轮询 |
| 经理 | 每个经理一个持久云端会话（`create_session`），有自己的 notes 文件 `docs/program/<步骤>.md` |
| 工人 | 经理用 `Agent`（`isolation: worktree`）开的子 agent，一个单元一个，做完即弃 |
| 审核 | 独立子 agent，不同模型，只拿 diff、产物、brief |
| 运营流水线 | 先由她每天说一声触发；连续几天自检通过、她同意以后，改成定时任务 |

agent 之间不互相传话。状态都在文件和 PR 里：经理读 PR 和 CI 结果，总协调读经理的汇总文件和 PR。

### 信任怎么积累、怎么升级

每个**角色**（例如「Greenhouse 适配器工人」「Workday 来源工人」「模型初筛」）和每个 **ATS** 各有一个信任等级，记在 `docs/program/scorecard.tsv`：

| 等级 | 角色的输出 | 升级条件 | 降级条件 |
|---|---|---|---|
| 0 新角色 | 审核者 + 总协调抽查，人工合入 | 连续 3 个单元首轮通过 | — |
| 1 可信 | 审核者通过 + CI 绿就自动合入 `v3` | 连续 10 个单元无缺陷，且对应的错误类都已有结构检查 | 被退回 2 次 → 回到 0、换模型或缩小单元 |
| 2 自主 | 经理可以直接派一批同类单元 | — | 合入后发现缺陷 → 回到 1 |

**投递**另走一条更严的阶梯，只有她能升级：`draft`（她看证据才提交）→ `auto`（某个 ATS 全绿就自动提交）。升级依据是这个 ATS 的提交审核记录：最近 N 份零错，确认邮件到达率达标。

### 让信任能积累的硬规则（写进代码和 CI，不写进文档）

1. **每个错误类第二次出现，就停下当前单元，先派一个结构单元。** 上一轮的「重复岗位」→ 所有来源的契约测试：岗位编号只能由 `jobKey(岗位自己的链接)` 生成；「误判下架」→ 只有 `BoardRead.complete` 能产生下架。
2. **每轮结束一行复盘**（`decisions.tsv`，phase=retro）：目标数字动了多少；这轮修的是尺子还是东西本身；有没有重复出现的错误类。**连续两轮目标数字不收敛 → 经理停止派活，上报总协调重新设计。**
3. **每个单元有 token 预算**，超了就停，交回原因。
4. **开长任务（完整搜索、全量抓取）之前，先写下跑完要做的决定。** 写不出来就不跑。
5. **审核清单里每一条，第二次用到时就变成测试**，审核者不再重复读。
6. **skill 也要 eval**：改一个角色的 skill 之前和之后，各用盲测跑一次（eval playbook：目录和 prompt 里不出现 test、eval 之类的字眼，另一个模型打分），分数不能降。

## 三、支撑这个组织的代码结构

多 agent 能并行的前提，是边界清楚、错误写不出来。

```
src/
  domain/     Company、Posting、BoardRead、Decision、Fact、Answer、Application、Submittable（纯，平台工人独占）
  policy/     eligibility、fit、每家公司上限、不投原因（纯，筛选经理）
  discover/   parse、merge、triage（纯，筛选经理）
  answer/     问题 → 事实映射（纯，投递经理）
  verify/     读回比对、gate、每日不变式（纯）
  sources/<来源>/   抓取器 + fixture + 契约测试（搜索经理，一个来源一个工人）
  ats/<名字>/       adapter + 浏览器端提取脚本 + fixture + ATS 地图 + e2e（投递经理，一个 ATS 一个工人）
  store/           ledger（只追加）、catalog、待办清单
  run/             day、apply（唯一会提交的地方）
  cli.ts
```

类型保证：
- `PostingId` 只能由 `jobKey()` 构造。
- 只有 `BoardRead.complete` 能证明一个岗位已下架。
- `Answer` 必须带 `FactId`。
- 只有 gate 能构造 `Submittable`，而 `adapter.submit()` 只接受它。

`npm run check` 要强制：
- import 边界。
- 每个来源目录、每个 ATS 目录都配齐 fixture、地图和测试。
- 注册表由目录生成。
- 每日页面的不变式。
- eval：筛选看标注集，答题看映射集，policy 看历史拒信回放；分数低于基线就不过。

**从 `v2` 带过来的**：`data/` 全部（不改）；所有抓取器和 ATS 提取脚本里踩坑得来的解析逻辑；真实页面 fixture；570 个测试，作为行为对照；「先写 ledger 再点提交」「`unconfirmed` 永不重试」；HANDOFF-v3 第四节和 `decisions.tsv` 里她的所有决定。
**不带过来的**：`rules.ts` 按措辞写的正则（由 `answer/` 取代）；`src/org/*`（脚本模拟的「经理」，由真正的 agent 会话取代）；过期的 handoff 和清单。

## 四、启动顺序（每一步都有能检验的出口）

| 步 | 谁 | 做什么 | 出口 |
|---|---|---|---|
| 0 | 总协调 + 1 个平台工人 | `v3` 骨架：`domain/` 类型、目录约定、生成式注册表、结构测试；录下 `v2` 的行为作为对照 | `npm run check` 绿；对照录制可以重复跑 |
| 1 | 搜索经理 + **1 个**工人 | 先迁一个来源（Greenhouse 板），走完任务书 → 工人 → 审核 → 合入整条链 | 该来源契约测试绿；对这些公司按公司验收「今天读全」；记下这条链的问题，修好任务书模板 |
| 2 | 搜索经理铺开 | 其余来源一个工人一个，同时最多 10 个 | 公司地图 × 今天读全（按 H-1B 申请量加权）≥95%；读不了的公司进她的手动名单 |
| 3 | 筛选经理 | 22 个误拒按规则归因、逐条修；拒信变成不投原因 | 抽样误拒 ≤5%；盲审误选 ≤10%；历史拒信回放全部能拦下 |
| 4 | 投递经理 | `answer/` 取代正则；先迁 Greenhouse，再逐个 ATS | verify-apply 在 fixture 和一个真实岗位的 draft 上全过；敏感题零错 |
| 5 | 运营组上线 | 每日流水线：她说一声就跑，产出每日页面和工单 | 连续 3 天不变式全过、无新的错误类 |
| 6 | 她 | 决定是否上定时任务，以及哪些 ATS 升到 auto | — |

步 0–1 是关键。视频里 Lauren 也是先让一个 agent 的输出可信，才同时开几十个。

## 五、需要她决定的

1. **Anduril 类岗位**：要求美国身份、出口管制许可、安全许可资格的岗位，一律不投？方案默认不投。另外，每家公司设投递上限吗（Waymo 投了 7 份，撞上了对方的申请数上限）？方案默认每家 3 份，按适配度最高的先投。
2. **代码 PR 自动合入**：角色升到等级 1 以后，审核通过 + CI 绿就自动合入 `v3`。代码可以撤回，所以默认允许；提交申请的自动化仍然只有她能放开。
3. **她手上的其他 skill 和资源**：拿到以后放进对应经理的 skill 里。
